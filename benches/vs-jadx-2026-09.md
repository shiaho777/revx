# revx vs jadx — 2026-09 实测基准

环境: macOS arm64, jadx 1.5.5 (OpenJDK 21), revx release (opt-level=z, Rust 1.97)。
样本: ToolTrove-73 APK (DEX 13.7MB + 4 native libs) 及王者荣耀 133-lib 语料。
所有数字为本机实测一次,非平均;revx 的 fast/full 由 budget 驱动,差距是刻意设计。

## 0. 先说清楚:两者不是同一赛道的工具

| | jadx | revx |
|---|---|---|
| 输入 | DEX/JAR/APK (Java/Kotlin 字节码) | ELF/PE/Mach-O 原生机器码 (ARM64/x64) |
| 输出语言 | Java | C 风格伪代码 |
| 中间表示 | JVM 字节码 (高级) | 寄存器级 IR (低级) |

jadx 拿到的是**已经结构化**的字节码(类/方法/异常表都是现成的),revx 拿到的是**裸机器码**,
函数边界都要自己恢复。这决定了质量的先天差距,下文质量对比必须在这个前提下读。

## 1. 性能 (同一 APK, 4 线程)

| 任务 | 工具 | 耗时 | 峰值内存 | 产出 |
|---|---|---|---|---|
| 全量反编译 APK DEX (5028 类) | jadx | **9.2s** | 150 MB | 7851 个 .java, 285k 行 |
| libcrypto_engine.so (63KB) full | revx | 0.08s | 9.7 MB | 40 函数, 40 伪代码 |
| libGameCore.so (79MB) fast | revx | **1.3s** | **9.4 MB** | 1024 函数 (预算封顶) |
| libGameCore.so (79MB) full, RSS=512MB | revx | 24.5s | 160 MB | **65,524 函数全恢复**, 0.32 覆盖率 |
| libil2cpp.so (217MB) full, RSS=512MB | revx | 48.1s | 324 MB | 65,504 函数, 32,091 typed |
| 同一 .so 喂给 jadx | jadx | — | — | **0 输出,不支持原生码** |

公平结论:
- 高级字节码赛道,jadx 快且省,9 秒吃完一个 APK,我们没有异议。
- 原生赛道 jadx 是 0,jadx 没有可比数据 — 这不是 revx 快,是 jadx 不玩这个。
- revx 的 8MB 档 fast 与 512MB 档 full 是同一个工具的两档,65k 函数全恢复 24.5s,
  折算吞吐 ~2,700 函数/秒;48s 吃完 217MB 的 il2cpp 是实测,不是宣传。

## 2. 反编译质量 (四维度,逐个诚实打分)

### 2.1 变量/符号命名 — jadx 完胜
- jadx (SafeNotificationChannels.ensure): 局部变量有类型推断名 (`notificationManager`,
  `notificationChannelM`),Kotlin metadata 恢复出原始类名,甚至保留了 lambda 结构。
- revx full-profile (NativeCrypto.decrypt): `arg_0`/`arg_2`/寄存器名,调用显示
  `GetStringChars(arg_0, arg_3, 0)` 但接收变量是 `r_GetStringChars` — 寄存器语义,
  非变量语义。同一调用点重复展开 3 次,无公共子表达式消除。
- **判定: jadx 9/10, revx 3/10。** 这是差距最大的一项,Issue #53 的主攻方向。

### 2.2 控制流还原 — jadx 完胜
- jadx: try/catch/lambda/协程挂起点还原为 Java 语法,几乎无损。
- revx: 基本 if/goto + `// bb1 @ 0x5298` 标签,循环无结构化(while/for 形态缺失),
  switch 未恢复成 case 组。
- **判定: jadx 9/10, revx 4/10。** 有 CFG (14 blocks 正确恢复) 但语法化不足。

### 2.3 类型信息 — 分赛道
- jadx: Java 类型系统现成,泛型擦除后仍恢复 `LruCache<String, String>`。
  但对 native 层无能为力,JNI 函数在 jadx 输出里只是一个 `System.loadLibrary` 字符串。
- revx: 无 metadata 时全是 `unknown_t`;**il2cpp metadata 存在时 typed_function_count
  32,091/65,504 (49%) 是 jadx 完全做不到的维度**。
- **判定: DEX 赛道 jadx 9/10; native+metadata 赛道 revx 6/10, jadx 无成绩。**

### 2.4 完成率/鲁棒性 — jadx 略优但两者都有伤口
- jadx: 7851 文件中 1683 个带 WARN (21%),38 个 ERROR,枚举恢复失败留下的
  `/* JADX WARN: Failed to restore enum class */` 原样可见 — 权威工具也在留伤。
- revx: fast 档预算封顶时函数只给 stub (`/* lean size=0xf8 */`),覆盖率 0.0044
  这种数字若不看文档会误导;packer 加密段如实报 not covered。
- **判定: jadx 7/10, revx 5/10。** jadx 伤口更多但产出基数大;revx 的 stub 在
  低预算下是设计行为,但"decompile 返回 lean stub"对用户是惊吓,应显式标注。

## 3. revx 独有而 jadx 没有的能力

| 能力 | 实测 |
|---|---|
| 原生 .so 函数恢复 | 65k 函数/79MB .so, 24.5s |
| il2cpp metadata 解析 (v20-31) | type/field/method 全量 |
| method-pointer 表 + 重定位扫描 | 133 语料 429 表/773,737 方法地址 |
| esp-offsets v1 导出 → esp-overlay 消费 | 互通验证通过 |
| 8MB RSS 档 | CI/笔记本全语料扫描 |
| MCP/agent 证据链 | evidence ID 全程可追溯 |

## 4. 结论(不偏不倚)

1. **jadx 在它的赛道(DEX)更强、更成熟、更快,没有争议。** 变量命名和控制流
   还原是十年的差距,不是几个 PR 能追平的。
2. **jadx 的赛道到 native 边界为止。** libil2cpp/libGameCore/加固 native 层,
   jadx 交白卷;这是 revx 存在的理由,也是 Issue #53 说"投入反编译"时应该
   圈定的范围 — **在 native 伪代码质量上做到第一,而不是去 DEX 赛道追 jadx。**
3. revx 当前最痛的三处(全部有数据支撑): 寄存器级伪代码缺变量语义、
   控制流未语法化、lean stub 对用户不透明。
4. jadx 的 21% WARN 率说明:反编译没有满分,竞争点在于谁的伤口更小、
   谁对伤口更诚实。revx 的 coverage 指标是这个方向的正确设计,应保留。

复跑方式: 本文件数据由一次性实测采集;脚本化复跑见 issue #53 的 benches 计划。
